# Floating windows are immediate egui viewports drawn by the one Shell

A Floating window (#152) is an egui **immediate** viewport (`Context::show_viewport_immediate`) that the main window's `Shell` shows every frame, with an `egui_tiles` tree of its own. Its Tabs are Tabs of the one Workspace in the one Session: Link sets, focus, commands, History and saving work across windows with no extra plumbing. The Workspace keeps each window's Panels and place (`Workspace::floating`, saved as `WorkspaceSnapshot::windows`), the same way it keeps the main window's `arrangement`. This amends ADR 0005, which noted that egui_tiles has no floating windows: we make them out of egui viewports instead of switching docking crates.

## Considered Options

- **Deferred viewports (`show_viewport_deferred`), as the ticket suggested:** each window repaints on its own, so a busy floating window never costs the main window a frame. But the callback must be `Send + Sync + 'static`, so the whole `Shell` (Session, User database connection, glyph atlas, every Tab's view) would have to live behind `Arc<Mutex<…>>`, and `UserData` and everything else in the Session would have to become `Send`. Every UI path, and the headless tests that drive `Shell` directly, would change; and where viewports are embedded (the web, tests) the callback runs inside the parent's frame, so the lock must be released around it.
- **Immediate viewports (chosen):** the callback borrows the `Shell` it is called from, so a floating window draws its Tabs with exactly the code the main window uses. The cost is that a floating window is redrawn whenever the main window is (and the other way round).
- **One OS window per Panel without an egui_tiles tree:** simpler, but a floating window could not hold several Panels and Tabs, which #152 asks for.

## Consequences

- With no floating window open the main window does no extra work per frame (`show_floating_windows` loops over an empty list), so the #19 frame targets are unchanged. A floating window costs what its visible Panels would cost if docked in the main window: Resource text is laid out and rasterized once and only drawn again from the glyph atlas, so idle frames do no text work in either window (tested).
- If floating windows ever need to repaint independently (an animation in one while the other is idle on a slow machine), moving to deferred viewports means making the Session `Send` first.
- Where the backend has no OS windows (the web, headless tests) egui embeds each viewport as an `egui::Window` in the main window; the same code runs, which is what the tests exercise. Such a window has no close button: Move to main window brings its Tabs back.
- Window places are stored in desktop units (the OS's window coordinates, the same on every monitor: pixels on Windows and Linux, points on macOS), with the monitor each window was on and its scale. egui points cannot be used: with monitors of different scale factors each window's points are its own pixels over its own scale. Places are converted to and from a window's points at that window's scale only, where egui-winit does the same. The app lists the connected monitors (winit through `eframe::Frame::winit_window`) only while floating windows are open; a window restored where no monitor is is moved onto the main window's monitor.
- One Shell draws every window, so what egui keeps per viewport (input, modifiers, text focus) must not be read from the main window while a floating one is drawn: the keyboard's Tab, the Ctrl/Cmd split modifier and the Note editor are per window (see `docs/dev/floating-windows.md`).
