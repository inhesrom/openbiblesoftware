# The app may ask GitHub for its latest release and replace its own Release archive

The app has kept to one rule since #1: it works offline and never phones home (ADR 0016). That left no way to learn that a newer version exists short of visiting the releases page, and no way to install one short of unpacking an archive by hand, so fixes (crashes, data-loss fixes like #252) never reached most users (#276). The maintainer decided to make one exception, for this purpose only. We decided:

1. **The Update check is the one network request the app makes by itself.** It is a plain HTTPS `GET` of public release metadata from this repository's GitHub releases API, sent through the app's own transport (the engine has no network code, #91, #219), on a background job:
   - `GET https://api.github.com/repos/inhesrom/openbiblesoftware/releases/latest`, or with **Include pre-releases** on, `GET https://api.github.com/repos/inhesrom/openbiblesoftware/releases?per_page=20`;
   - with the headers `User-Agent: OpenBible/<version>` (GitHub refuses requests without one), `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2022-11-28`, and the transport's own `Accept-Encoding`. No cookie, token, identifier, telemetry or usage data is sent; GitHub sees the computer's IP address and the app version, as for any download.
2. **Check for updates automatically is on by default** (maintainer decision). With it on, every launch makes exactly one check, on a worker thread, three seconds after the first window appears, so it never delays startup; a launch check that cannot reach GitHub stays quiet. The first launch that checks says so once, with Turn off. **Settings → Updates** has the switch and **Include pre-releases** (off). With the switch off the app makes no network request at all unless the user clicks **Help → Check for updates…** (or Settings → Updates → Check for updates).
3. **A newer version is offered, never forced.** The tag is compared with the app's version as semver; drafts, older and equal versions are never offered, pre-releases only when the user opted in. The update notice (a window at the bottom right that does not block the app) shows the version, its release notes and **Update now**, **Later** and **Skip this version**; a skipped version is remembered in the User database and not offered again at launch (Help → Check for updates… still shows it), and a newer one is.
4. **Update now replaces a Release archive in place, after verifying it.** Only assets of a published, non-draft release of this repository, under `https://github.com/inhesrom/openbiblesoftware/releases/download/`, over HTTPS, are fetched: `SHA256SUMS` and the archive for this platform and architecture (`openbible-<tag>-<target>.tar.gz`, or `.zip` on Windows), with a progress bar and Cancel. The archive's SHA-256 must be the one `SHA256SUMS` lists before anything is unpacked. It is unpacked into `.openbible-update/new` beside the executable (entries that would land outside it are refused); then, on the UI thread, a **Before-update backup** of the User database is taken (ADR 0013's backups, kept in the same list, the last five), and each top-level entry of the new folder (the executable, `starter/`, the licence files, the install marker) is renamed into place, the old one moved aside into the update folder first. Renaming works on a running executable on Linux, macOS and Windows (Windows refuses only to overwrite or delete it); on any failure everything moved so far is moved back; if even that fails, the replaced files stay in `.openbible-update/old` with a note (`rollback-incomplete.txt`), are never deleted by the launch clean-up, and no further Update now is offered until the user sorts it out from the download page. **Restart now** first saves a Note being written and the Last session, then starts the new executable with the same arguments and closes the app, so the new process never reads them before they are written. The next launch deletes what was replaced, the old Windows executable included. The Library, the User database and the settings are never touched by the update, beyond the backup; newer Starter Resources in the new `starter/` reach the Library through the existing Starter library flow (ADR 0007).
5. **Only a Release archive updates itself.** `cargo xtask release-archive` puts an install marker, `openbible-install.json` (`{"kind": "archive"}`), beside the executable. A copy without it (a build from source, a distribution's package), on a platform without a published archive, or in a folder the user cannot write, is told about the new version and offered **Open the download page** instead of Update now. The installers of #272 (`.app`/`.dmg`, `.msi`, AppImage) plug in as further kinds of that marker, each with its own way to replace itself (a quiet `msiexec`, a whole `.app` bundle that keeps its quarantine and notarization, the AppImage file); the check, verification, backup and notice are shared.
6. **Release signing: the verifier ships now, the key comes later.** The app verifies a detached **minisign** signature of `SHA256SUMS` (`SHA256SUMS.minisig`) with a public key compiled into it (`RELEASE_PUBLIC_KEY` in `obs_engine::updates`) before trusting any checksum in it; a missing or bad signature refuses the update. The `release` workflow signs `SHA256SUMS` with `minisign` when the `MINISIGN_SECRET_KEY` Actions secret exists and skips the step cleanly (with a notice in the run) when it does not. Until the maintainer creates the key and the secret (the commands are in `docs/dev/releasing.md`) and compiles the public key in, the app verifies `SHA256SUMS` only, and the update notice says so: "Release signing is not set up yet." A checksum from the same release page does not stop a compromised release; the signature will.
7. **Every failure leaves the old version running** and says what went wrong in plain words, with Open the download page: offline, rate-limited by GitHub (HTTP 429, or 403 with no requests remaining), no release yet, no download for this computer, checksum mismatch, bad signature, no permission to change the folder, a damaged archive, cancelled. Nothing downloaded is run before it is verified and installed, and a version is never replaced by an older or the same one.

## Considered Options

- **Stay offline; announce releases only on the website:** keeps the rule, but fixes never reach the users who need them most, and an offline-first app still has to be updatable.
- **Check off by default, or ask on first run before any check:** the maintainer decided on by default, with the first check announced once and one switch to turn it off; a user who turns it off gets no network traffic at all.
- **A project update server or a feed of our own:** one more thing to run and trust; GitHub's releases are where the archives already are.
- **A self-update crate (`self_update`, `velopack`, a Sparkle/WinSparkle per platform):** pulls a network client and archive handling into the library layers or a second process per platform, and none of them knows the Starter library beside the binary. The archive swap is a few renames we can test end to end on all three OSes.
- **Download to a temporary file and copy over the installed files:** Windows cannot overwrite a running executable, and a half-copied folder is worse than either version. Renaming within one folder is quick and can be undone.
- **Sigstore (keyless) signing:** verifying it needs a transparency-log client and certificates in the app; minisign needs one 32-byte key and a few kilobytes of code, and the key can be rotated with a release.

## Consequences

- CONTEXT.md now states this exception to the offline rule. ADR 0016 still holds for Crash reports: nothing about a crash is ever sent by the app. Any other network use still needs its own decision.
- The release workflow fails a tag whose version is not the workspace version, since an app that misreads its own version would offer itself as an update forever.
- `cargo xtask update-e2e` builds the app as this version and as the next patch version (`OBS_BUILD_VERSION`), installs the first from a Release archive, serves the second from a mock release source on localhost (`OBS_UPDATE_URL`) and checks that Update now and Restart now leave the next version running with the user's data intact; CI runs it on Linux, macOS and Windows. Unit and UI tests use an in-memory mock release source; no test talks to GitHub.
- `OBS_UPDATE_URL` names another release source, for tests. The compiled-in public key still applies to it, so once signing is set up it cannot install an unsigned build; only a debug build also takes `OBS_UPDATE_PUBLIC_KEY`.
- An archive downloaded by the app itself carries no quarantine attribute on macOS, so the updated plain binary runs as the old one did; the `.app` bundle path (#272) must keep Gatekeeper's checks.
- Until the release key exists, an attacker who controls the GitHub release can ship a matching archive and `SHA256SUMS`; the notice says the download is checked against checksums only.
